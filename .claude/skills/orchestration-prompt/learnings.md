# orchestration-prompt learnings (project-scoped)

Append one-line lessons as you generate prompts. Keep them project-scoped; never
bleed across repos. This file is created once by the scaffolder and never
overwritten on upgrade — it's yours.

- Multi-epic single-repo drives: sequential `/goal` (not Workflow coding fan-out); override per-edit `tapps_quick_check` to story/epic gates when the epic itself targets gate latency. (2026-07-30)
- Metrics follow-on epics: order root-cause false-positive flags (diff_impact 100% degraded) before surfacing completeness UX, or agents paper over bad semantics. (2026-07-30)
- Reachability test on *reduction* targets: split the metric into reducible vs irreducible before writing a number into Done-when. A "36K→8K tool schema" target was unreachable — 7.8K of the 36K was param schedule, not prose; the honest floor was 16K. Chasing the bad number would have burned the budget deleting parameters. (2026-08-07) Same move one level down, at the *predicate*: before widening a validator, state in advance which rows of its control matrix may flip, then run the matrix against both the old and the new implementation. A 15-row matrix with "exactly two rows may flip" written down beforehand, and exactly two flipping, turns "did I widen this correctly?" from a judgement into a measurement — and costs one extra run. (2026-09-17)
- Reordering sub-goals after the contract table is written silently breaks the fulfills-coverage mapping. Re-run the coverage check *after* any resequencing, not just at first draft. (2026-08-07)
- When the epic edits the harness it runs under (hook/skill templates), add an explicit "do not run `tapps_upgrade` mid-loop" guardrail plus the deploy-lag note — measure from source via a committed script, deploy only at the end. (2026-08-07)

- [high] **A worktree dispatch needs its `.mcp.json` headers rewritten, not just copied.** `.mcp.json` is gitignored, so a `git worktree` has none — and copying it verbatim is *worse than missing*: all six `X-Tapps-Project-Root` headers still name the original checkout, so every `tapps_*` gate call scores the wrong tree and returns a meaningless green. Copy it, rewrite the six headers to the worktree path, `uv sync` (a fresh worktree has no `.venv`), then prove it by asserting `tapps_session_start().project_root == <worktree>`. Encode that assertion as a required-fail cap in Sub-goal 0 of any worktree run. Worktree isolation is the right move whenever another session already holds the main checkout. — (urgent-high-burndown, 2026-08-26)

- [high] **Check whether a "fix" already exists in a consumer repo before scoping it here.** TAP-6498 (Urgent) and TAP-6496 read as greenfield, but both were already implemented and merged in WebStoreDNA's *scaffolded copies* (PRs #125/#124) while this repo's canonical generator still carried the old behaviour — so the real work was a port-back with a working reference implementation, not a fresh build. Linear `attachments[]` is where this surfaces; read it before estimating. The asymmetry is itself a filed defect (TAP-6497, managed-block markers), which is why port-backs must sequence *after* it — otherwise `tapps_upgrade` eats the consumer fix and recreates the defect. — (urgent-high-burndown, 2026-08-26)

- [high] **Two file counts can agree while the two trees differ — one file swapped for another.** `plugin/claude/.mcp.json` was matched by `.gitignore:55` and silently dropped from the commit, so the shipped bundle declared no MCP server while 26 skills, 5 agents and 13 hooks all depended on one. The lane reported "55 tracked files" from the builder's `files_created` side and never re-derived it from the committed side; `git ls-files` said 54, a fresh build said 54, and `diff -r` was exactly two rows — `Only in plugin/claude/.claude-plugin: marketplace.json` / `Only in buildC: .mcp.json`. A count comparison passed *because* the swap was one-for-one. Never compare a build to a commit by `wc -l`: sort both relative-path lists and `comm -3` them, and run `git check-ignore -v <path>` on any build output you intend to track. Encode it as a path-set regression test, not a count assertion — a count assertion cannot catch this class. (2026-09-16) Sharpened: the same count also has several *simultaneously correct* answers, one per population, so publish the command beside the number. A shipped README claimed "103 skills and 7 agents, counted directly from this bundle's `skills/` and `agents/`" when under that stated population the true values are 92 and 0; three different greps returned 103/7, 98/1 and 92/0, every one arithmetically right for a different set. Any number written into an artifact needs the one-line command that reproduces it printed next to it, or a reader cannot tell which set was counted — and neither can its author a week later. (2026-09-17)

- [high] **A number restated outside the code that computes it cannot move, and will be reported as equal on both sides.** A lane twice offered `context_floor_skills.py description_bytes` as byte-identity evidence — "5901 == 5901 over 24/32", then "7761 == 7761 over 32/32", plus a 24→32 "progression". All of it was unreproducible: on base the script raises `MeasurementError: tapps-finish-task: no description field in frontmatter` on the *first* dict key, because `_leading_literal` follows only `BinOp.left` and stops at the `"model: "` fragment before `resolve_role_model()` is spliced in. No script in the repo can produce a base-side number, partial or otherwise. The refactor's byte-identity was in fact real — established independently by manifest diffs and golden sha256 hashes — so the false line changed no conclusion, which is exactly why it survived two rounds of the author's own review. Before citing any base-vs-branch equality, run the measuring script against *both* trees yourself; if one side cannot be measured at all, the equality is fabricated. (2026-09-16) Sharpened — the *reason* given above is itself wrong, and was wrong on its own face: a walk that follows only `BinOp.left` never inspects the non-leftmost operands, so it returns the truncated leftmost literal, it does not raise. "Follows only `.left`, so a spliced call makes it raise" is two halves of one sentence contradicting each other, and four rounds of work chased the raise. A wrong mechanism attached to a right conclusion survives review exactly as well as a right one. When a premise names a code path, open the path and check that the clause after the "so" actually follows from the clause before it — before any lane acts on either. (2026-09-17)

- [high] **Never anchor a plan on a function without grepping for its call sites.** The driving prompt asserted, as a verified correction, that `generate_claude_plugin_bundle()` "is already exposed as a CLI command `build-plugin`". It is not: `cli_ops_build.py:31` imports `PluginBuilder`, and `grep -rn generate_claude_plugin_bundle src/` returns only its own definition plus a re-export shelf — **zero production call sites**. Two independent Claude bundlers existed, and the one the prompt named as working was the one nobody had ever run; the other turned out to emit a `hooks.json` referencing `.claude/hooks/*.sh` scripts it never shipped, behind a green unit suite that only asserted its own wrong shape. One `grep -rn "<symbol>" src/` before writing the plan would have caught it. Corollary: a shipped function with no caller has never been exercised, so treat "it already exists" as untested, never as working. (2026-09-16)

- [high] **A schema validator passes a bundle that is missing the things it depends on.** `claude plugin validate --strict` returned RC=0 on all four targets (plugin.json, marketplace.json, skills/, agents/) while the bundle shipped no MCP config, no LICENSE despite both manifests declaring `"license": "MIT"`, and no CHANGELOG. It checks manifest and component *shape*; it never cross-references what else the bundle ships, nor whether a referenced server or tool name resolves. Use it as ground truth for schema — do not hand-reimplement it — but pair it with a step that resolves every path a manifest references against the shipped tree, and one human-shaped read asking whether the artifact is the thing that was asked for. Here that read found 15/26 skills and 5/5 agents referencing `mcp__nlt-build__*` while the shipped `.mcp.json` registers `tapps-mcp` — a private fleet alias that would fail to resolve for every external installer, invisible to every gate. (2026-09-16) Sharpened — the blind spot is wider than `--strict`, and wider than schema. On a later bundle `claude plugin validate --strict`, a bespoke in-repo validator, and `claude plugin install` itself **all three exited 0**; only `claude plugin list` run *after* the install reported `✘ failed to load`. `--strict` also does not resolve dependencies at all — a manifest declaring a dependency on `totally-bogus-plugin@^99.99.99` passes it clean. Installability is not loadability: end every bundle gate with an install-then-list round trip against a throwaway profile, and read the list output, not the install exit code. (2026-09-17)

- [high] **A test result is a bucket — both a red test's name and a green pass count conceal their population.** Comparing failed-test-ID *sets* across base and head — the same discipline that correctly exonerated another PR that day — reported "no new failure" while the branch had in fact added one: `test_pyinstaller_spec.py::TestSpecCompleteness::test_all_modules_have_hidden_imports` failed at base with `1 module(s) missing: tapps_mcp.project.static_detectors` and at head with `2 module(s) missing`. Same ID both sides; one more defect inside it. Diff the failure's *content*, not its identity — and treat a long-red gate as a hiding place rather than as untidiness, because every defect it will ever absorb arrives under a name that is already on the allowed list. The green side fails the same way: a lane reported "403 passed" having introduced four failures, because its own selection excluded the two files that held them — the full path-scoped run was `5 failed, 8950 passed`. Never accept a pass count whose selector is unstated, and re-run the full path-scoped suite before any "no regression" claim. (2026-09-17)

- [high] **One observation of the external system beats any number of in-repo restatements of it.** `init_permissions.py:16`, `platform_hook_templates.py:339-341` and `plugin/claude/CHANGELOG.md:9` all agreed that a plugin's MCP tools are addressed as `mcp__tapps-mcp__`. All three were wrong — the real shape is `mcp__plugin_<pluginName>_<serverKey>__` — and they agreed only because they are three copies of one belief, not three witnesses. It was settled in minutes by building a throwaway plugin, installing it, and watching a tool return `pong` inside a `stream-json` `tool_use` block. For any fact owned by a system outside this repo (a CLI's naming scheme, an API's wire shape, a host's resolution rules), budget one live round-trip and take that as ground truth; N grep hits corroborate nothing but each other. (2026-09-17)

- [high] **Put the guard where the information still exists — a check that reads the parsed value inherits every position the parser discarded.** A sentinel substituted for statically-unresolvable frontmatter text was silently dropped from a `description: >-` block scalar, because `_fold_block_scalar` continues the fold only `while startswith('  ') or not strip()` and a sentinel-bearing line is neither; the guard inspected the folded value, saw nothing, and never fired. Four successive fixes each handled the case they named and broke an adjacent one, all for that one reason — the guard kept being re-placed downstream of the loss. Before fixing, name the property that must survive (here: the sentinel's *position in the raw span*) and assert on the text before the transform. Then ask of each candidate fix "can this now produce a wrong number instead of failing loudly?" — that question found a regression that re-running the lane's own proof never would have. (2026-09-17)

- [high] **A control whose fixture cannot build the failing state is not discriminating — it is guessing.** An "anti-vacuity" control asserting that a bare `mcp__tapps-mcp__` reference is rejected only ever built a fixture that was *also* undocumented, so a rejection could not distinguish "rejected because bare" from "rejected because undocumented". A later fixture that was bare *and* documented passed clean — precisely the case the check existed to catch. Before a control's verdict is allowed to mean anything, write down the states its fixture never creates (absent, fresh, already-done, documented-but-wrong, mid-operation), build one of them, and require the verdict to change. (2026-09-17)

- [high] **Audit the set of files that assert the claim, not the artifact you were pointed at.** Three independent verifiers read `plugin/claude/README.md` — one of them hunting specifically for user-facing false claims, and it found one there. All three walked past the repo-root `README.md`, which carried the same now-false claim and is the first file a new user opens. A reviewer scoped by filename inherits the judgement of whoever chose that filename, and three reviewers given the same filename inherit it three times. Scope the audit by the claim instead: `grep -rn "<the claim string>" .`, then reconcile every hit, including the ones outside the directory under review. (2026-09-17)

- [med] **A percentage is not a quantity — cap the cumulative absolute, never the share.** The orchestrator reported its own token share (~15%) every iteration, and that number stayed reassuring while cumulative program spend passed **three times** its stated cap unremarked, because the denominator grew without bound. A ratio, a rate, and a per-lane average are all incapable of tripping a ceiling. Any budget clause in a prompt must name an absolute total and be re-measured as a running sum at every checkpoint, with the check written as "cumulative >= cap → stop", not "share looks normal". (2026-09-17)

- [med] **Verify the default branch before writing `origin/main` into a prompt.** Four sub-goals of the driving prompt specified worktrees off `origin/main`; tapps-mcp's default is `master` and `origin/main` does not exist, so every lane would have failed at its first command. `git symbolic-ref refs/remotes/origin/HEAD` costs nothing. Same class: `tapps_session_start(project_root=...)` silently ignores that argument and bootstraps whichever repo the *launching session's* `.mcp.json` pins, so a driver running from another repo gets gate verdicts scoped to the wrong tree — assert `project_root` in the response equals the tree you mean before trusting any verdict built on it. (2026-09-16)
