# orchestration-prompt learnings (project-scoped)

Append one-line lessons as you generate prompts. Keep them project-scoped; never
bleed across repos. This file is created once by the scaffolder and never
overwritten on upgrade — it's yours.

- Multi-epic single-repo drives: sequential `/goal` (not Workflow coding fan-out); override per-edit `tapps_quick_check` to story/epic gates when the epic itself targets gate latency. (2026-07-30)
- Metrics follow-on epics: order root-cause false-positive flags (diff_impact 100% degraded) before surfacing completeness UX, or agents paper over bad semantics. (2026-07-30)
- Reachability test on *reduction* targets: split the metric into reducible vs irreducible before writing a number into Done-when. A "36K→8K tool schema" target was unreachable — 7.8K of the 36K was param schedule, not prose; the honest floor was 16K. Chasing the bad number would have burned the budget deleting parameters. (2026-08-07)
- Reordering sub-goals after the contract table is written silently breaks the fulfills-coverage mapping. Re-run the coverage check *after* any resequencing, not just at first draft. (2026-08-07)
- When the epic edits the harness it runs under (hook/skill templates), add an explicit "do not run `tapps_upgrade` mid-loop" guardrail plus the deploy-lag note — measure from source via a committed script, deploy only at the end. (2026-08-07)

- [high] **A worktree dispatch needs its `.mcp.json` headers rewritten, not just copied.** `.mcp.json` is gitignored, so a `git worktree` has none — and copying it verbatim is *worse than missing*: all six `X-Tapps-Project-Root` headers still name the original checkout, so every `tapps_*` gate call scores the wrong tree and returns a meaningless green. Copy it, rewrite the six headers to the worktree path, `uv sync` (a fresh worktree has no `.venv`), then prove it by asserting `tapps_session_start().project_root == <worktree>`. Encode that assertion as a required-fail cap in Sub-goal 0 of any worktree run. Worktree isolation is the right move whenever another session already holds the main checkout. — (urgent-high-burndown, 2026-08-26)

- [high] **Check whether a "fix" already exists in a consumer repo before scoping it here.** TAP-6498 (Urgent) and TAP-6496 read as greenfield, but both were already implemented and merged in WebStoreDNA's *scaffolded copies* (PRs #125/#124) while this repo's canonical generator still carried the old behaviour — so the real work was a port-back with a working reference implementation, not a fresh build. Linear `attachments[]` is where this surfaces; read it before estimating. The asymmetry is itself a filed defect (TAP-6497, managed-block markers), which is why port-backs must sequence *after* it — otherwise `tapps_upgrade` eats the consumer fix and recreates the defect. — (urgent-high-burndown, 2026-08-26)

- [high] **Two file counts can agree while the two trees differ — one file swapped for another.** `plugin/claude/.mcp.json` was matched by `.gitignore:55` and silently dropped from the commit, so the shipped bundle declared no MCP server while 26 skills, 5 agents and 13 hooks all depended on one. The lane reported "55 tracked files" from the builder's `files_created` side and never re-derived it from the committed side; `git ls-files` said 54, a fresh build said 54, and `diff -r` was exactly two rows — `Only in plugin/claude/.claude-plugin: marketplace.json` / `Only in buildC: .mcp.json`. A count comparison passed *because* the swap was one-for-one. Never compare a build to a commit by `wc -l`: sort both relative-path lists and `comm -3` them, and run `git check-ignore -v <path>` on any build output you intend to track. Encode it as a path-set regression test, not a count assertion — a count assertion cannot catch this class. (2026-09-16)

- [high] **A number restated outside the code that computes it cannot move, and will be reported as equal on both sides.** A lane twice offered `context_floor_skills.py description_bytes` as byte-identity evidence — "5901 == 5901 over 24/32", then "7761 == 7761 over 32/32", plus a 24→32 "progression". All of it was unreproducible: on base the script raises `MeasurementError: tapps-finish-task: no description field in frontmatter` on the *first* dict key, because `_leading_literal` follows only `BinOp.left` and stops at the `"model: "` fragment before `resolve_role_model()` is spliced in. No script in the repo can produce a base-side number, partial or otherwise. The refactor's byte-identity was in fact real — established independently by manifest diffs and golden sha256 hashes — so the false line changed no conclusion, which is exactly why it survived two rounds of the author's own review. Before citing any base-vs-branch equality, run the measuring script against *both* trees yourself; if one side cannot be measured at all, the equality is fabricated. (2026-09-16)

- [high] **Never anchor a plan on a function without grepping for its call sites.** The driving prompt asserted, as a verified correction, that `generate_claude_plugin_bundle()` "is already exposed as a CLI command `build-plugin`". It is not: `cli_ops_build.py:31` imports `PluginBuilder`, and `grep -rn generate_claude_plugin_bundle src/` returns only its own definition plus a re-export shelf — **zero production call sites**. Two independent Claude bundlers existed, and the one the prompt named as working was the one nobody had ever run; the other turned out to emit a `hooks.json` referencing `.claude/hooks/*.sh` scripts it never shipped, behind a green unit suite that only asserted its own wrong shape. One `grep -rn "<symbol>" src/` before writing the plan would have caught it. Corollary: a shipped function with no caller has never been exercised, so treat "it already exists" as untested, never as working. (2026-09-16)

- [high] **A schema validator passes a bundle that is missing the things it depends on.** `claude plugin validate --strict` returned RC=0 on all four targets (plugin.json, marketplace.json, skills/, agents/) while the bundle shipped no MCP config, no LICENSE despite both manifests declaring `"license": "MIT"`, and no CHANGELOG. It checks manifest and component *shape*; it never cross-references what else the bundle ships, nor whether a referenced server or tool name resolves. Use it as ground truth for schema — do not hand-reimplement it — but pair it with a step that resolves every path a manifest references against the shipped tree, and one human-shaped read asking whether the artifact is the thing that was asked for. Here that read found 15/26 skills and 5/5 agents referencing `mcp__nlt-build__*` while the shipped `.mcp.json` registers `tapps-mcp` — a private fleet alias that would fail to resolve for every external installer, invisible to every gate. (2026-09-16)

- [med] **Verify the default branch before writing `origin/main` into a prompt.** Four sub-goals of the driving prompt specified worktrees off `origin/main`; tapps-mcp's default is `master` and `origin/main` does not exist, so every lane would have failed at its first command. `git symbolic-ref refs/remotes/origin/HEAD` costs nothing. Same class: `tapps_session_start(project_root=...)` silently ignores that argument and bootstraps whichever repo the *launching session's* `.mcp.json` pins, so a driver running from another repo gets gate verdicts scoped to the wrong tree — assert `project_root` in the response equals the tree you mean before trusting any verdict built on it. (2026-09-16)
