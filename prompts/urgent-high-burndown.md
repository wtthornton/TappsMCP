## Loop

- **State:** wayfind resume recall → `linear-read` cache-first for the project → brain recall of
  prior attempts on this issue → last handoff → `git log -1`.
- **Decide:** take the next undone issue **in wave order**. Never start wave N+1 while a wave-N
  issue is unverified. Within a wave, respect the stated ordering (5841 → 6497; 5659 first in W2).
- **Execute:** branch, re-read the issue's `## Where` anchors against live code (hard-stop if
  they no longer match), fix the root cause, run `tapps_validate_changed` on the changed files,
  push, open a PR.
- **Verify (independent):** spawn a fresh-context verifier (`general-purpose`, `opus`, high)
  prompted to **refute** the proof. Hand it the **exact proof command**, the expected artifact,
  the `file:line` anchors from the issue's `## Where`, and the environment quirks (which
  interpreter, `uv run` prefix, non-default ports, where `.venv` lives). Never hand it your own
  narrative — a fresh context that gets a story reasons about plausibility instead of running
  anything. Its report must quote the output it actually observed. **Its verdict advances the
  loop, not your claim.**
- **Merge:** only after the verifier confirms — squash-merge, then re-check Done-when clause 3
  (collect count) **before** starting the next issue.
- **Record:** comment the evidence on the Linear issue, set it Done via the `linear-issue` skill,
  invalidate the snapshot cache, write the structured handoff to brain.
- **On fail (expected-fail fix loop):** structured handoff → narrow fix sub-goal → re-execute →
  re-verify; **≤3 validation rounds per issue**, then escalate once (`opus` → `fable`), then stop
  with a diagnosis, leave the issue In Progress with a comment naming what was tried, and move on.
  Never weaken the contract to go green.
- **Context hygiene:** prune stale reads each iteration; targeted grep over full re-Read; carry a
  compact state summary, not raw transcripts. Delegate noisy multi-file reads to `Explore`.
- **Print every iteration:** `SCORE: <n>/25 issues Done · wave <k>/5 · tests <collected> (floor 11454) · round <a>/3 · iteration <i>/60`
- **Checkpoint:** at each **wave boundary** or ~50% context — whichever first.
- **Repeat or stop:** loop until Done-when holds; caps: **60 iterations** AND **~2.5M output
  tokens**, both **cumulative across shifts**, read from the handoff, never reset by a clear.

## Checkpoint protocol

- **Lane:** *declared checkpoint* — the loop prints the block below and stops; the operator types
  `/clear`. An agent cannot invoke `/clear` itself, so never instruct yourself to.
- **Trigger:** wave boundary, or ~50% context — whichever first.
- **Write:** `/tapps-handoff-session`. **Resume:** `/tapps-continue-session`.
- **Carry-forward (must survive the clear, or the guardrails stop binding):**
  - Current wave + the VAL IDs still red
  - Attempt count vs cap — **cumulative** (`round 2 of 3` for TAP-####)
  - Budget spent — **cumulative**
  - Strategies already tried and refuted, and why
  - The running test-collect count vs the 11,454 floor
  - The exact resume line from "How to run (cold start)"
- **On resume, re-verify before acting:** re-check `git rev-parse --short HEAD`, open PRs, and
  whether another session has taken the checkout. A claim true at checkpoint can be false an hour
  later. The independent verifier still runs; a checkpoint never replaces it.

```
CHECKPOINT <n> — wave <k> complete. Handoff written.
Cumulative: round <a> of 3 · iteration <i>/60 · tests <collected>/11454 floor.
Next: /clear   then   /tapps-continue-session
```

- Discipline: root-cause not workarounds; no green-by-suppression; right-sized; durable; match

## Autonomy

- Act on every reversible, in-scope step — branch, fix, push, open a PR, verify, comment on Linear.
  No "should I proceed?" checkpoints.
- Merging to `master` **is** authorized for this loop, but only **after** an independent verifier
  confirms the proof. An unverified merge is a hard-stop violation, not a shortcut.
- Hard-stop once (batched, with a recommendation) for: another session holding this checkout · a
  fix that cannot be made without weakening a gate or deleting tests · the test floor dropping
  below 11,454 · projected next-step cost above the ceiling (≈USD 20) · the validation contract
  itself turning out to be wrong · fog returning on an in-scope issue · any temptation to pull in
  TAP-6062 or to edit a sibling repo.

## Failure handling

- On failed verify: diagnose (read the actual error + inspect state + brain recall) → form a
  specific hypothesis → fix → retry with *something changed*. Never re-run the same action on the
  same error.
- ≤3 distinct strategies per issue; then escalate once (`opus` → `fable`); then stop with a concise
  diagnosis and move to the next issue.
- Expected-fail: the first verify failing is normal, not a crisis. Scope a narrow fix; do not
  reopen the whole issue and do not rewrite the contract.
